## 负向发现与修复

第一次真实 canary 已成功完成 provider 请求，但课程断言错误要求 `request/context.length >= 2`，因此 demo 在验收阶段失败。

复核固定上游语义后确认：`request/context` 是 route facts 的持久快照，不是“每次 provider 请求一条”的计数器。修复为：

- `request/context` 只验证至少存在一条且 provider/model 正确；
- 模型请求次数改从每条 `assistant/message.usage` 汇总；
- usage calls 同时受 `maxStepsPerTurn = 3` 上界约束。

修复后以及最终复审后的真实 canary 均通过。该失败没有通过放宽工具证据掩盖；`tool/call`、CallId 配对、工具结果、最终文本与 usage 仍全部必须成立。

## 安全与费用边界

- `.env` 与 `.dsh/` 被忽略，`.env.example` 的 Key 值必须为空。
- 课程解析函数只返回 provider/model，不返回或打印 Key。
- CLI 的 provider 失败只回显稳定 code，不转述自定义网关的原始错误正文，避免响应内容反射到终端。
- 官方默认端点与自定义 `DEEPSEEK_BASE_URL` 都会收到 Key、Prompt、工具 schema / 结果、anonymous user id 与 session id；自定义配置只是改变接收方，只能指向可信端点。
- 仓库根 `.env` 只适合本章无文件能力的 `course_add` canary；未来接入 filesystem / shell 工具时，Secret 必须移出 Agent 可访问工作区，不能把 `.gitignore` 或文件权限冒充工具级访问控制。
- 512 token 与 3 Step 是费用和失控保护，不代表免费；真实调用仍受余额、限流、网络和模型随机性影响。
- CI 绿色只证明 keyless plumbing；本次真实 canary 才是当前 provider 可用证据，两者不能互相替代。
- `git diff --check` 与 Secret pattern scan 通过；production audit 为 0 个已知漏洞，license inventory 仍为 MIT、BSD-2-Clause、BSD-3-Clause 与 ISC。
